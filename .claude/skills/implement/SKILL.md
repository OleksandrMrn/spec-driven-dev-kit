---
name: implement
description: Implement an approved plan from docs/specs one session at a time, with scoped verification and self-review. Use only when invoked explicitly.
argument-hint: "<TICKET> [S<n> | T<n>] [what to fix]"
disable-model-invocation: true
---

Implement the approved plan for the ticket given with the invocation (`$ARGUMENTS`: `<TICKET>`, optionally one session `S<n>` or a single task `T<n>`, and, for a fixes run, what to fix), one session per run, the fixes run excepted (`docs/specs/README.md`, "Sessions").

1. Find the ticket folder `docs/specs/<TICKET>-*/`; unless exactly one matches, stop and say so. Read `AGENTS.md` (sections 2.4 to 2.7, 3, 4 and 9), the folder's `spec.md` and `plan.md`, and the ADRs the spec lists.
2. Check both statuses. Stop and say so unless the spec is `approved` and the plan is `approved` or `implemented` (fixes after review; the approval stays in force, AGENTS.md section 2.3). A `draft` spec next to an approved plan means the spec changed after the plan was approved: the spec is approved again first, then the plan is checked against it and approved again (`docs/specs/README.md`, "Statuses").
3. Pick the work of this run. The state is what is on disk, also after an interrupted run: the ticks, "Results and deviations" and the working tree (AGENTS.md section 2.4); what an earlier run did not record is checked, not assumed.
   - Fixes named in the invocation or, on an `implemented` plan, by the review: the tasks the findings touch. This is the one exception to one session per run: the fixes may touch tasks of several sessions, since every session touched is checked again.
   - `T<n>`: that task; if it is ticked, a fix of it, and the invocation says what to fix.
   - Otherwise a session: `S<n>` if given, else the first of "Sessions" with an unticked task. A session runs only when every earlier session has "Checked" filled; otherwise stop and name the session that waits for the person's check. A session whose tasks are all ticked is a fixes run on it, and the invocation says what to fix. When no session is given and no task is unticked, the run finishes the plan: the whole verification of the plan (step 5), the self-review against the spec (step 6) and the status (step 7).
   A ticked task that the run changes is unticked before the change and the "Checked" of its session cleared, so the person checks it again; it is ticked again when its fix has passed the scoped verification.
4. Execute the work: the unticked tasks of the session in order, the single task, or the fixes. Everything stays within the files listed in the plan and the approved scope; minimal sufficient change; anything outside the plan goes into the report, not into the diff. A review finding that changes requirements, scope or approach is not implemented: it goes back to the spec or plan, which is set to `draft` and approved again. A conflict with an accepted ADR stops the work and is reported (`docs/specs/README.md`, "ADRs"). Tick a task in `plan.md` only when it is done and its scoped verification (step 5) has passed, the known baseline of AGENTS.md section 9 excepted. The next session is not started in this run, however much context is left; only a fixes run (step 3) touches several sessions.
5. After each task run the scoped verification from the plan (the commands of AGENTS.md section 9); after the last session, and in the run that finishes the plan, the whole verification of the plan. A failing check is understood first, not patched around.
6. When the session's tasks are ticked, and after a fixes run, do the self-review of AGENTS.md section 2.6 against the requirements and acceptance criteria its tasks map to; after the last session, and in the run that finishes the plan, against the whole spec. A fix made in the self-review re-runs the checks it affects (AGENTS.md section 2.5).
7. Write the results into `plan.md`, section "Results and deviations", as one entry per run (`Run <k>, <date>, S<n> (T<a>–T<b>)`, `T<n>`, `fix after review`, `fix after the check` or `finishing run`, with the session and tasks), appended to what earlier runs wrote: what was verified and how, what was not and why, deviations and their reason, fixes after review with the finding each answers, out-of-scope findings. Set `status: implemented` only when every task of the plan is ticked and every verification of the plan has passed; the only failures allowed are the known baseline of AGENTS.md section 9, each named in the results. Otherwise the plan is unfinished: on an `approved` plan the status stays; on an `implemented` plan (a fixes run that left a new failure, a check not run or a fix half done) set `status: approved` and untick the tasks whose requirements the fix touches, so the approval stays and the plan shows what is open. In both cases name the tasks that remain, what fails or what was not run; a run that stops before its work is done also writes the unfinished action and the next command or check (AGENTS.md section 2.4).
8. No commits and no PRs. Report per AGENTS.md section 2.7, with the session's "Check" as what the person verifies next and a note that the next session starts with a new run once "Checked" is filled, then stop. Whether to commit between sessions is the person's call: do not ask. After the last session ask whether to commit and open a PR; either happens only on an explicit yes (AGENTS.md section 6).
